# 26.3.25-replay.1：数据库牌谱、桌面回放与 AI 分析

基于 26.3.24 的试验分支 `codex/mahjong-replay-analysis`。此版本没有合并至 main，也没有安装到正式服务器。

## 使用

1. 在此版本中新开一场三麻或四麻，正常打至整场终盘的“对局结束”。牌谱自动归档；手动结束、重置和预设练习局不计入完整对局。
2. 通过牌桌菜单领取“牌谱”，或使用原来的八纸围红中配方合成。主手持有后右键空气或牌桌，打开“我的麻将概况”，点击“我的牌谱”。旧牌谱物品同样进入该界面，不再读写牌桌配置。
3. 日历沿用任务模组签到页的 54 格布局，日期从第 2 行顺排。红中表示当天有参与的完整对局，白板表示没有；物品名为完整日期，可翻月。
4. 当日记录按结束时间从新到旧排列，每页五场。每行第 1 格载入，第 2–5 格为东、南、西、北风牌，物品名为终局分数，说明显示玩家名；三麻未使用的北位显示“—”。第 6 格发财切换该场的 AI 分析，再点击载入。
5. 载入前准备 8 格内归自己所有、没有正在进行的对局或其他真人占座的空闲牌桌。多张符合条件时选最近的一张。

牌谱按 Quest 配置的时区、对局结束时的自然日期归档，默认 `Asia/Shanghai`。不使用签到的凌晨 4 点切日规则。只有实际参与者能在自己的日历中查询、载入该场牌谱，中途接替的真人也计入参与者。

## 桌沿回放

桌沿提供：开始、上一步、下一步、终局；上一局、播放/暂停、下一局、倍速；视角、全手牌显示、分析开关、退出。倍速为 0.5、1、2、4 倍。手动跳转暂停播放，终点自动暂停，终点再次播放从头开始。另可通过桌主菜单打开同一组回放控制。

回放按已记录的状态前进和倒退，恢复牌山、手牌、摸牌、牌河、副露、宝牌、立直与供托、局场和比分，不重新运行机器人或重新随机发牌。控制仅桌主可操作，附近玩家可观看。视角选择公开相应座位手牌，显示全部时公开四家；开启分析时也会公开当前出牌者的手牌以显示推荐。

回放与实战鸣牌按钮共用 `TableEdgeButtons`：同一布局、文字、交互体和射线命中检查。退出后清除回放，保留目标牌桌的库存、规则、座位及桌主；回放本身不计入战绩。

## 分析口径

采用用户确认的相对最优 0–99 分，四舍五入显示整数，最高 99。每次实战弃牌按当时局面的对应候选计分，每位玩家每局取实战弃牌分数的算术平均。没有弃牌的阶段不生成虚假分数。局内均分显示于比分 HUD。

四麻复用当前高级 `majiang-ai`，仅传当时本人手牌和公共可见信息。保留原 AI 的防守推荐为第一候选、99 分。其余候选使用收益与危险度计算相对效用：

```text
效用 = max(0, EV) × exp(-3 × max(0, 向听增加值)) / (1 + 危险度 / 3.2)
分数 = round(99 × 候选效用 / 最大候选效用)，限制在 0–99
```

三麻复用现有 Java 向听与可见进张评估，使用三麻实际牌种；没有将三人局伪装为四人局输入高级 AI。这是相对决策质量评分，EV 和显示分数均不代表和牌胜率。

当前出牌阶段最多显示三个不同候选：最优绿色 `▼`，其余黄色 `▼`，整数分数在箭头上方，分数背景宽度等于一张牌的宽度。原始相对分低于 1 的候选不显示。全部玩家的弃牌后台逐步分析，当前查看帧优先，结果按牌谱和版本缓存至数据库。

分析使用独立有界队列和 Node 进程，不占实战机器人工作线程。Node 缺失、计算超时和响应错误时显示分析不可用，不伪造评分；回放仍可使用。首次整场分析需要等待后台计算，已完成部分的分数会逐步出现。

## 数据库与恢复

只读服务器现有 `config/timory_quest_server.json` 中的 `database` 和 `timezone`。支持该配置的 MySQL/MariaDB 主库；不生成另一份含密码配置，不修改 Quest 配置或业务表。MySQL Connector/J 26.7.0 以现有 Quest 相同的嵌套驱动包随模组分发。

首次连接会幂等建立三张表：

| 表 | 内容 |
| --- | --- |
| `riichi_replays` | UUID、开始/结束时间、规则、版本化压缩全信息牌谱 |
| `riichi_replay_players` | 参与玩家 UUID、座位、名称、终局分数及名次、查询索引 |
| `riichi_replay_analysis` | 版本化分析缓存 |

账号需要在原有数据库中建这三张表的 `CREATE` 权限，以及这些表的 `SELECT`、`INSERT`、`DELETE` 权限。程序不创建数据库、不修改已有表，不需要额外整库授权。

逐动作记录挂到规则驱动内部，覆盖一个 tick 内接受的多个动作；采集过程随方块实体存档保存。自然完局先保存可恢复的待归档记录，写入世界目录 `data/riichi-replay-outbox/` 并获得持久化确认后再移除桌子的待归档项。SQL 写入使用事务和 UUID 幂等处理，断库保留 outbox 并重试，未落盘的队列拒绝/磁盘故障不会被当成归档成功。

旧版已经开始的牌局没有完整动作历史，不会伪装成完整牌谱归档。牌谱物品仅为入口，完整暗牌和数据库凭据不会放进物品数据或公共方块更新包。

## 构建与验证

配置环境见 `BUILDING.md`，在项目目录执行：

```text
node build.cjs
node test.cjs
node test-replay-database.cjs /path/to/h2-2.3.232.jar
```

数据库测试使用独立 H2 MySQL 模式和临时文件，不连接现有服务器数据库。H2 仅用于测试，不打包进模组。输出为 `build/verification.json` 和 `build/replay-database-verification.json`，并记录实际 JAR 的 SHA-256。

本次构建通过 26 组 Java 回归、13 项 Node 测试和 22 项独立数据库检查。自动验证覆盖三麻/四麻完整记录、单 tick 多动作、存档恢复、回放前后与跨局控制、归档拒绝与恢复、数据库事务/幂等/参与者过滤/分页/时区、四麻真实 AI 与三麻评分、分析缓存、Node 缺失/超时/错误响应。尚未进行真实客户端的菜单点击、桌面箭头与文字视觉验收，也未在现有正式 MySQL/MariaDB 上执行建表或联调。
